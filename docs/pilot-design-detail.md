# Pilot 监督详细设计

> #510 已取代本文的自动唤醒、每项目 Pilot、冷却及唤醒状态方案。当前能力以 [平台 steward](pilot-design.md) 为准；用户定期检查由 #511 单独交付。下文保留为历史设计。

本记录整理自 [#407](https://github.com/zhoushoujianwork/clawflow/issues/407) 及其补充意见。除 [概要中的 P1](pilot-design.md) 外，下述均为目标设计，不代表已经交付的能力。后续切片以各自议题的最新决策为准，尤其是 #409 对动作及 override_merge 的修订。

## 背景与执行

2026-10-27 自托管 ClawFlow、Agent-Host、offload 和 GitLab pop 时，人工外部监督会话承担了这些工作。目标是由每个协调器的一个 Pilot 接替，使用独立、较强的模型 profile；实现代理继续使用较快的默认 profile。设计举例是 Codex `gpt-6.1-sol`、`high` 推理，实际模型不写死，任意 Offload profile（含 ACP）均可。

目标输入是各仓库 main 的干净只读检出、看板快照（#401）、自上次唤醒以来的运行日志、验收摘要和代理 BLOCKED 评论。当前按项目每轮唤醒、通过 CLI 直接写 VCS 的方式将在后续切片替换。

## 八项职责

1. 健康与恢复：检查服务、代理和调度器活性；超过 30 分钟无日志进展时诊断，例如阻塞 45 分钟的 git fetch。提出 `restart_service`，进程级恢复仍由代码负责（#403）。
2. 解阻：对队头 agent-failed、blocked 验收、重试耗尽和队列阻塞，读取证据并区分环境/沙箱限制、暂时性基础设施故障、规格缺口或错误假设、真实产品缺陷、需要人决策。采取决策与释放、规格修订或一个精确问题。案例包括 offload #20 的重试链假设及 Agent-Host #15 的 Python 3.9 SQLite WAL / 沙箱 ps 限制。
3. 队列维护：补全 Decided、验收条件和文件指针，拆分过大任务，按优先级、依赖和可并行关系排序，暂缓纯设计项。
4. 提前可行性研究：对队头前 1–2 位的大任务只读研究并写回议题，例如 #385 拆分为 #385/#398/#399。
5. 系统性诊断：从跨运行的重复模式建立根因议题，例如 #397 unsupported_tools、#403 无界 git、#404/#406 暂时故障变硬阻塞、运行未合并分支构建的 Offload。
6. 策略约束合并：#407 原始提案仅允许启动、暂时或环境问题造成的卡住；须确认 CI 成功、对照规格审查 diff、绑定审查过的 head、发布审计评论并关联根因议题。默认关闭，原设计开关为 `pilot.override_merge: on`；不得绕过真实未修复缺陷。具体落地策略与配置命名由 #409/#411 的最新契约决定，P1 不实现或启用此开关。
7. 合并后运维：仓库在 ClawFlow 自身合并之外前进时安装/升级，空闲时重启服务。
8. 报告：每次简报、每日摘要和看板 Needs attention 中的人类问题（#402）。

Pilot 不实现代码，不审查自己制定的实现，不修改门禁或仓库设置，不为让 PR 通过而放宽验收条件；后者必须由人决策。

## 代理提议，代码执行

目标输出是 fenced `pilot-actions` JSON 块。确定性代码校验 schema、允许列表、每次/每日限额和策略，执行后写 `pilot/action` 审计（包含 run id、结果）并供看板展示。未知或禁止动作被拒绝并报告；移除提示词中的直接 VCS 写入指令。

初始动作：`comment`、`release`（附原因解除 agent-failed/agent-skipped）、`edit_spec`（替换/追加议题正文的标记区段）、`create_issue`、`queue_add`、`queue_move`、`queue_remove`、`label_add`/`label_remove`（允许列表）、`ask_human`、`restart_service`、`override_merge`（策略门禁）和 `note`。

规格决策必须通过 edit_spec 修改正文，不能仅留评论：验收契约读取正文。offload #20/#22 与 clawflow #418 的教训是评论中删除的要求仍可能被验收读取。#409 后续增加的 rerun_ci、CLI apply 和结构化 finding locations 不在 P1 范围内。

## 唤醒

目标是在现有预算和冷却限制内按事件唤醒：新增 attention 项（失败、阻塞、重试耗尽、队列阻塞），停滞轮次（超过 30 分钟），任务到达 head-2 仍无 Decided，未入队的新议题，PR 非终态卡住超过 1 小时，以及每日摘要。没有变化时不唤醒。

## 分期与验证

- P1 / #408：独立 pilot 角色、profile 路由与回退、execution check、配置/API 展示及设计文档。测试覆盖路由、默认回退、环境优先级、检查输出、唤醒角色。
- P2 / #409：结构化动作解析、允许列表、策略、限额、审计和执行器，移除直接 CLI 写入。以其最新范围补充为准。
- P3 / #410：事件驱动唤醒和职责 1–5、7、8；使用 2026-10-27 案例记录验证动作计划。
- P4 / #411：职责 6 的合并门禁及看板动作/问题集成，避免重复 P2 已吸收的范围。

本地测试、独立验收和真实 GitHub Actions 证据分别记录；本地通过不等同于 CI 或真实监督交付成功。
