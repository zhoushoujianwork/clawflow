# Watchdog：发现卡住的任务

状态：第 1、2 步已在代码中实现，但尚未部署，只观察、不处理。阈值校准和自动处理还没有开始。[实现说明](watchdog-design-detail.md)记录规则、接口和验证情况。

## 目标

任务卡住时，平台应尽快自己发现并说清原因，不必等到执行超时，也不必等人来问。现在租约、熔断和修复预算能处理崩溃和重复失败，但一个任务如果活着却没有进展，可能要到超时才暴露；恢复和写回停滞多久，也没有统一的判断。

## 使用方式

用户不需要配置或确认任何东西。原生 App 继续显示任务状态，并多显示一条原因，例如“Watchdog: recovery pending for 45 min.”。这些原因也会写入 `~/.clawflow/logs/watchdog.log`，并可通过看板接口读取。

## 核心方案

Watchdog 是 controller 内的确定性检查，不是新的 Agent，也不调用模型。它必须在模型或 Offload 故障时继续工作，也不能增加常驻 token 成本。

| | Watchdog | Pilot |
| --- | --- | --- |
| 触发 | controller 持续运行 | 用户提问或用户定义的检查 |
| 判断 | 固定规则 | 模型结合上下文分析 |
| 动作 | 记录原因；校准后才进入现有恢复流程 | 解释原因，执行受策略约束的操作 |

Pilot 仍然不会被自动唤醒。Watchdog 不启动新任务，也不新增恢复路径。

三条边界不变：

- 不能只因 heartbeat 丢失或暂时没有事件就重派任务，避免重复执行。
- 不修改 `clawflow-skip`，不绕过 CI、独立验收和合并检查。
- 预算耗尽时进入有原因的阻塞状态，不增加人工确认步骤。

## 本期范围

本期只观察和显示：恢复停滞、结果写回停滞、派发停滞，以及之后的远端任务无进展。

本期不做这些：

- **目标漂移检测：** 先由独立验收在交付时把关。等真实运行记录证明验收来不及止损时，再评估模型监督。
- **自动处理：** 误报率有数据之前，不取消或恢复任何任务。
- **任务来源授权和 PR 评论直达：** 这是相邻的独立工作，不放进本设计。

## 实施顺序

1. **用现有数据观察。** 从看板快照推导恢复、写回和派发三类异常，不改表结构。
2. **补上远端进度。** worker 通过独立接口尽力上报距上次事件的时长，失败不影响任务。旧 worker 不上报时视为未知，不判定异常。
3. **校准。** 结合现有的一周、至少 20 个真实任务的观察，确认阈值和误报率，并单独记录结果。
4. **再决定是否自动处理。** 只有证据足够时，才让明确的异常进入现有恢复流程，并沿用现有预算；这一步需要单独确认，不随前面的改动自动启用。

任务来源授权是安全问题，建议排在第 1 步之前。这只调整整体推进顺序，不影响本设计。
