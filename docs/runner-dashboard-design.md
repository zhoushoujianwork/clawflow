# Runner 风格的阶段看板与执行终端

目标是让用户直接看懂“正在做什么、卡在哪里、实际执行了什么”。列表参考 GitLab Jobs：等高行、固定状态列和耗时列，任务标题占用剩余宽度；不再用窄任务列表搭配长期空白的详情面板。

## 使用方式

看板展示任务、当前阶段、Runner、状态与本次耗时。点开任务查看详情。后续同一 issue / PR 下分阶段展示检查、实现、PR 审核，以及必要的修复、再次审核；每个阶段可以有多次独立执行。

每次执行提供一个只读的内置日志终端，类似 Runner Job 日志：进入时回放，执行中持续追加，可暂停跟随、滚动查看、按工具调用展开输出。内容来自该次 Offload 执行，不以调度事件代替。关闭终端不取消任务。

## 状态与范围

阶段和执行分开：实现完成不代表 CI、审核或合并完成；未开始、跳过、失败和等待必须明确区分。重试是新执行，不能把上一轮日志拼到当前轮。历史缺少证据时显示未知，不补造阶段结果。

本地第一版交付全宽任务/Runner 表格、统一尺寸、阶段筛选和详情。当前服务只能提供实现、PR 审核、修复、回复的任务类型；独立检查阶段尚无完整投影。详情里的调度事件每 5 秒刷新，并明确区分尚未接入的 Offload 输出。

完整执行终端尚未上线。接入顺序是：Offload 按次采集 → worker 按所属执行读取并同步 → controller 鉴权、分页与回放 → App 内置终端。验收必须覆盖真实任务运行中输出、断线续读和重试隔离后，才能称为上线；只改 App 或 Offload 支持读取都不算完成。

实现约束与验收见[详细设计](runner-dashboard-design-detail.md)。
