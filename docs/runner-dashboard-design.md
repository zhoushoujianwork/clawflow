# Runner 风格的阶段看板与执行终端

目标是让用户直接看懂“正在做什么、卡在哪里、实际执行了什么”。主看板参考 GitLab Pipelines：每个 Issue 一行，展示当前活动和各阶段摘要；Job 列表放在 Pipeline 内部，不再把每次执行平铺成主看板。

## 使用方式

每个 Issue 是一条 Pipeline。点开后按检查、实现、PR 审核展示阶段，并保留必要的修复、再次审核。阶段内每次执行是一个 Job，单独展示 Runner、本次耗时、重试次数与日志入口。检查阶段可以包含检查 Job，但不能把实现内部未上报的检查步骤猜成独立执行。

完整终端的设计是：每次执行提供一个只读的内置日志终端，类似 Runner Job 日志：进入时回放，执行中持续追加，可暂停跟随、滚动查看、按工具调用展开输出。内容来自该次 Offload 执行，不以调度事件代替。关闭终端不取消任务。

## 状态与范围

阶段和执行分开：实现完成不代表 CI、审核或合并完成；未开始、跳过、失败和等待必须明确区分。重试是新执行，不能把上一轮日志拼到当前轮。历史缺少证据时显示未知，不补造阶段结果。

本地版交付按仓库和 Issue 聚合的 Pipeline 表格与阶段详情；同一 Issue 的实现、修复、审核 Job 归入同一行，尚无 Job 的排队 Issue 也可见。Job 成功不把 Pipeline 标成通过。当前原生快照尚未接入已有交付投影，也缺少独立检查阶段证据，这些状态明确显示未上报。Job 详情里的调度事件每 5 秒刷新，并明确区分尚未接入的 Offload 输出。

完整执行终端尚未上线。接入顺序是：Offload 按次采集 → worker 按所属执行读取并同步 → controller 鉴权、分页与回放 → App 内置终端。验收必须覆盖真实任务运行中输出、断线续读和重试隔离后，才能称为上线；只改 App 或 Offload 支持读取都不算完成。

实现约束与验收见[详细设计](runner-dashboard-design-detail.md)。
