# 本机无人值守开发闭环

目标是让用户描述任务、配置权限和预算后，ClawFlow 能持续完成开发、检查、有限修复和交付，并把真实阻塞清楚展示出来。无人值守不意味着绕过验收或无限重试。

[实现与验收说明](managed-development-design-detail.md)记录恢复约束和验收边界；[实际部署记录](unattended-deployment-2026-11-02.md)记录已验证版本与尚未完成的证据。

## 使用方式

用户在项目中提交 Issue，通过原生 macOS App 查看进度、worker、排队原因和 PR。符合条件的任务由现有本机 controller 调度，开发与审核通过 Offload 执行。需要用户决定范围、补足环境或处理预算耗尽时，任务明确停在可解释的阻塞状态。

## 核心方案

- 一个本机 controller 负责调度与状态，独立 worker 执行任务；App 是控制客户端。
- CI、独立验收、开发来源与合并权限分别检查，不能互相替代。
- 执行记录支持恢复与结果重放；升级仍须检查部署协议并排空旧执行器，不能假设所有历史进程都能安全重启。
- 当前部署使用 PostgreSQL。存储迁移单独设计和验收，不混入本期交付。

## 本期范围

优先完成同仓 GitHub PR 的正常交付、CI 修复、验收修复、重启恢复。保留已有 GitLab 运维和兼容能力，但不以扩展它们作为本期完成条件。

多 controller、一万 worker、工作流市场和 Web 控制面扩展移出当前方案；历史草案保留在 Git 历史中。现阶段先证明本机持续运行可靠，再根据实际瓶颈决定扩容。

## 实施顺序

1. 对齐已部署 controller/worker 版本，修复真实运行中发现的问题，保留来源与独立验收证据。
2. 验证四条真实链路，确认中断不会重复执行、错误验收不会启动无意义修复。
3. 观察一周并累计至少 20 个真实任务，记录成功、阻塞、人工介入和恢复结果，再判断是否达到无人值守目标。

这是一组验收目标，不是已达成声明；一次部署或单个 PR 成功不能替代持续运行证据。
